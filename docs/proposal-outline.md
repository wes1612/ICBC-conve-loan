
# 项目策划书框架

## 1. 项目背景
- **1.1 背景介绍**：
  消费扩容与服务业升级背景；普惠金融支持小微主体的政策方向；本地生活服务商户在扩大消费供给中的作用；传统授信方式对轻资产服务商户的覆盖不足。
- **1.2 小微服务商户现状调研**：
  咨询公司研报结果 + 我们的走访结果；\
  总结目标商户的经营特征、融资需求、还款来源和主要痛点。
- **1.3 竞品分析**：
  建行平台快贷、蚂蚁网商贷、美团金融；
- **1.4 总结**：
  工行可通过“银行数据 + 平台数据 + 消费场景 + 线下服务能力”形成差异化方案，将授信从单纯资金支持延伸为经营诊断、消费承接和动态风控闭环。

## 4. 数据体系与规则基础
- **4.1 结构化数据**：
  主体信息、经营流水、税票信息、平台订单、核销率、退款率、现金流入流出、账户余额、负债情况、经营计划和资金用途。
- **4.2 非结构化数据**：
  营业执照、合同、发票、评价文本、投诉记录、社媒内容、经营说明、门店图片和补充材料。
- **4.3 数据清洗与一致性校验**：
  对主体名称、法人信息、门店地址、收款账户、订单、发票、流水和合同进行交叉验证；不一致时降低置信度或进入人工审核。
- **4.4 评分计算规则**：
  围绕稳定性、成长性、真实性、消费承接能力、口碑社媒投诉、数据完整性和法人授信状态展开；评分规则应版本化，避免前端、数据库和后端出现多套口径。
- **4.5 授信额度规则**：
  额度应综合月均经营收入、经营性净现金流、负债压力、收入波动、成长性、消费承接能力和风险调整系数形成；建议输出额度区间或建议额度，并说明形成原因。
- **4.6 人工审核规则**：
  主体不一致、异常交易、高退款高投诉、现金流恶化、材料缺失、法人信用异常、数据低置信度、命中一票否决规则等情形进入人工复核。
- **4.7 模拟数据与真实数据边界**：
  五个模拟商户用于开发、演示和验收，不用于声称已经训练真实违约或欺诈模型；当前 `pd_12m` 应保持未校准状态。

## 5. 技术架构
- **5.1 技术架构综述**：
  前端 React + 后端 FastAPI + SQLite/文件数据 + 版本化 ML 接口；整体目标是形成可解释、可审计、可联调的授信分析系统。
- **5.2 前端设计**：
  包括申请流程、资料上传、授权页、身份核验、分析结果页、授信报告、消费策略、银行审核视角和打印报告能力；页面流程应服务贷款对象、贷款场景和风控闭环。
- **5.3 数据库设计**：
  包括结构化 SQLite、非结构化 SQLite、模拟交易明细、月度现金流记录、原始 Excel 数据字典和测试商户数据；正式上线需扩展申请表、文件表、分析结果表、审批表和贷后监测表。
- **5.4 后端设计**：
  FastAPI 路由、schema 校验、特征工程、评分引擎、异常引擎、资金缺口引擎和聚合服务；核心计算逻辑应由确定性代码和规则引擎完成。
- **5.5 联调说明**：
  以 `POST /api/v1/ml/full-analysis` 为综合分析入口；Swagger/OpenAPI 和样例 JSON 固化前后端契约；前端不得自行复制评分权重和额度公式。
- **5.6 大语言模型（LLM）的应用**：
  用于材料抽取、评价投诉总结、经营计划归纳、报告文本生成和风险原因解释；LLM 不直接决定分数、额度、拒贷或人工审核结论。
- **5.7 机器学习技术（ML）的应用**：
  以可解释金融风控方案呈现评分卡、规则门控、MAD 异常识别、阻尼趋势预测和压力情景分析；明确当前 `pd_12m` 为 `UNCALIBRATED`，不能展示为真实违约概率。
- **5.8 测试验收**：
  五个模拟商户验收、后端单元测试、HTTP 冒烟测试、OpenAPI 导出、前端构建检查和端到端联调；后续应补充异常数据、缺失数据和冲突数据测试。

## 6. 系统运行流程
- **6.1 运行流程概览**：
  商户提交资料 → 系统校验资料完整性 → 数据清洗与标准化 → 形成统一特征快照 → 运行评分、异常识别和资金缺口预测 → 规则门控 → 输出授信建议和消费策略 → 银行审核 → 贷后监测。
- **6.2 资料提交**：
  商户填写主体信息、融资需求和资金用途；上传营业执照、流水、资产负债表、现金流量表、税票、合同、评价投诉等材料。
- **6.3 数据授权**：
  商户授权工行账户、支付结算、平台经营、税票和第三方工商司法等数据；授权失败或数据不可用时进入补件或人工审核。
- **6.4 数据清洗**：
  系统完成字段标准化、文件解析、缺失识别、异常值处理、主体一致性校验和跨数据源交叉验证。
- **6.5 特征评估**：
  后端生成经营稳定性、成长性、真实性、消费承接能力、口碑社媒投诉、现金流和数据完整性等特征。
- **6.6 评分报告输出**：
  系统输出经营信用分、风险带、建议额度、置信度、人工审核规则、异常证据、未来三个月资金缺口和消费策略。
- **6.7 客户端常态化管理**：
  商户端展示授信结果、经营诊断、补件要求、消费策略、提额路径和贷后反馈。
- **6.8 贷后监测**：
  系统按月或按数据更新节点监测流水、订单、退款、投诉、现金流、额度使用和还款表现，触发提额、维持、降额、冻结或人工复核。

## 7. 应用拓展前景
- **7.1 商户分类与全周期个性化提升**：
  针对优质稳定型、成长型、风险型、资料缺失型和异常型商户，输出不同额度策略、补件要求、消费承接策略和贷后管理路径。
- **7.2 银行贷款业务全链条升级**：
  用证据链和模型版本辅助客户经理调查、审批人员复核、风控人员预警和贷后人员管理，提高小微信贷的可解释性和运营效率。
- **7.3 工行内部能力复用**：
  在合规前提下，将评分、异常识别、资金缺口预测和报告生成能力复用至普惠金融、收单商户、数字供应链、商户经营服务等内部场景。
- **7.4 跨行业拓展**：
  在首期生活服务行业验证后，逐步扩展至零售、餐饮、教育培训、家政维修、文娱健身等行业；不同业态需调整特征、规则和准入标准。
- **7.5 平台合作拓展**：
  与本地生活平台、支付机构、行业 SaaS 和政策服务平台合作，拓展订单、核销、评价、库存、预约和经营管理数据来源。

## 8. 技术拓展前景
- **8.1 数据接入**：
  从模拟数据扩展到工行账户、支付结算、税票、平台授权、工商司法和征信授权数据；正式接入前需完成数据授权、脱敏、安全和合规审查。
- **8.2 模型升级**：
  在真实贷后标签积累后，训练并校准真实 PD 模型；当前阶段只输出经营信用分、风险带和未校准状态，不声称已有真实违约概率。
- **8.3 运营闭环**：
  把授信、支付、结算、收单、工资代发、信用卡权益、商户经营服务和政策申报连接起来，形成工行服务小微商户的综合经营平台。
- **8.4 模型治理与审计**：
  建立模型版本、规则版本、数据版本、接口日志、人工审批和报告留痕机制，保证结果可追溯、可解释、可复核。
- **8.5 信息安全与隐私保护**：
  通过权限隔离、加密存储、访问控制、脱敏展示、审计日志和数据保留策略保障商户数据安全；区块链可作为远期探索，不作为首期核心技术依赖。

## 9. 风险、不足与改进
- **9.1 当前项目边界**：
  当前系统以模拟数据和规则模型为主，已实现评分、异常识别、资金缺口预测和前后端联调，但尚未接入真实银行账户、真实平台接口和真实贷后标签。
- **9.2 产品风险**：
  目标客群、首期行业、贷款参数、还款方式和资金用途管理仍需进一步收敛，否则容易从授信产品变成泛经营分析工具。
- **9.3 风控风险**：
  需要补充拒贷边界、人工复核机制、贷后预警处置、异常数据处理、授权失败处理和风险底线。
- **9.4 合规风险**：
  需要明确数据授权、隐私保护、模型解释、审批留痕、客户告知、拒贷原因说明和监管审查口径。
- **9.5 技术风险**：
  文件上传解析、真实接口接入、LLM 输出稳定性、模型版本管理、日志审计和部署安全仍需完善。
- **9.6 后续改进方向**：
  下一步应优先补齐产品参数、首期试点行业、风控闭环、银行端审核流程、贷后监测规则和真实上传解析能力。
